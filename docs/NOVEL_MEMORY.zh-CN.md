# 作品知识（Novel memory）

[English](NOVEL_MEMORY.md) | 简体中文

墨伴可以在你写作的过程中持续维护一部作品的知识：发生过什么、东西在哪里、人物
之间是什么关系、各人物知道些什么，以及你作为作者认定为真的设定。生成时会取用
写到当前位置为止成立的那部分知识，而不必为每次请求重读整部正文。

背后的引擎是 Recanta，一个私有的记忆内核，在构建时与编译成 WebAssembly 的
SQLite 一起嵌入插件，因此桌面端和移动端运行的是同一个引擎，不需要另外安装、
下载或更新。墨伴通过一个适配器使用它，并在其上负责一部小说所需的全部判断：
什么算正文、什么算设定，一句话处在故事的哪个位置，属于谁的视角，以及两条互相
矛盾的事实以谁为准。

## 你需要做什么

**建立一次。** 打开正文中的一章，运行「建立作品知识」。该章所在的顶层文件夹成为
正文范围，名字形如 设定 / 人物 / canon / world 的同级文件夹成为作者设定。两者都
记录在 `WritingBuddy/memory/novel/project.md` 里。
建立会把每一章和每一篇设定各读一遍，使用你为新对话设定的默认连接。没有默认连接
时，书目依然会建立，从其他设备同步来的知识也照常可用；只有阅读新文本才需要模型。

**建立耗时较长，而且消耗 token。** 作品知识是实验性功能，首次建立是花钱的那一步：
每约 3000 字算一段，一段一次模型请求，长篇就意味着几百次请求、较长的等待和大量
输出 token。桌面端一次读六章；在手机上，或通过本机模型时，一次读一章。开始之前，
插件会先统计范围——多少章、多少篇设定、多少段——并请你确认。运行期间，设置 →
项目数据和对话标题下的那一行会显示进度（第 3/30 篇、第 12/153 段）并带一个「暂停」；
命令面板里也有「暂停建立作品知识」。暂停落在下一段的边界，已经读过的内容全部保留，
因此「继续」只为从未请求过的部分付费。停用插件同样等于暂停。被暂停的建立，或因为
关闭 Obsidian 而中断的建立，都不会自己继续：重新打开仓库时会看到提示，设置里有
「继续」，在你按下之前不会发出任何请求。首次建立完成之后，章节更新的开销很小，
会自动进行。

**然后照常写作。** 每次保存都会被察觉、合并（连续多次保存算作一次工作），并且只
处理改动的部分。重命名和移动不会改变章节的身份。删除一章会让它的知识退场；放回去
则无需模型即可恢复。采纳 AI 的候选内容会写入文件，该文件与其他任何编辑一样被处理；
没有采纳的候选永远不会被记住。

**出问题的时候。** 对话标题下有一行安静的提示，写着「正在建立」「正在更新本章」或
「部分章节未能处理」并附「重试」。「重建作品知识」（命令，以及设置 → 项目数据里的
按钮）会丢弃本地索引，并从可同步的文件重新构建。没有仪表盘，也没有需要审批的东西。

**全稿分析是另一项独立操作。** 输入区的上下文选项是「自动」或「精简」。要就整部作品
提问，在输入区写下问题并运行「全稿分析（Full）」；自动模式的回合若发现需要完整覆盖，
仍会提议以这种方式继续。

## 一次生成会收到什么

一次生成按这个顺序组装：你选中的文本及其上下文、当前章节、相关的作者设定、来自
作品且符合故事位置的知识，以及在知识需要佐证时的少量原文段落。作品知识作为一条
证据送入，按类别分组：

| 类别 | 含义 | 来源 |
|---|---|---|
| 作者更正 | 你明确更正过的内容 | 你的更正记录 |
| 作者设定 | 你认定为真的内容 | 设定文件夹 |
| 当前叙事状态 | 到此为止事情处于什么状态 | 正文 |
| 正文事件 | 发生了什么，按故事顺序 | 正文 |
| 关系轨迹 | 两人之间如何，以及如何变化 | 正文 |
| 线索 | 未了结与已了结的情节线 | 正文 |
| 视角知识 | 当前章节的人物知道或相信什么 | 正文 |
| 推导观察 | 置信度较低的推断 | 推导范围 |

两条边界始终成立。**位置：** 比你正在写的位置更靠后的知识，由引擎本身扣下——在
第二十二章才被挪走的钥匙，在你写第二十一章时仍在盒子里。章节内部，边界是光标
所在的那一段。**视角：** 某个人物知道或相信什么，只在你正写这个人物的章节时返回；
其他人物的私有知识，以及别人被告知的谎言，都会隐去。较低类别与较高类别在同一件事
上不一致时，会作为矛盾标注在较高类别旁边；设定绝不会被正文偶然的说法覆盖，而明确
的作者更正高于设定。

正文在多章里陈述过的同一件事是一条事实、多个位置，因此一段反复的关系读起来是
`信任 → 猜疑 → 信任`。修改前面的章节使其不再陈述某条事实，会让该章的支撑退场；
仍在陈述它的后续章节会让它继续成立。

## 东西存放在哪里

| 位置 | 内容 | 是否同步 |
|---|---|---|
| `WritingBuddy/memory/novel/project.md` | 项目清单：正文范围、设定文件夹、建立状态、写入这些知识的引擎 | 是 |
| `WritingBuddy/memory/novel/sources/<id>.md` | 每章或每篇设定一个包：身份、路径、故事顺序、视角、最后处理的正文版本，以及在代码块中的全部 Recanta 制品（来源版本、抽取运行、事实变迁、生命周期事件） | 是 |
| `WritingBuddy/memory/novel/corrections/<id>.md` | 你的明确更正，按同样方式打包 | 是 |
| `.writing-buddy-cache/novel/<book>/` | 本地索引：引擎数据库、已加载内容、待处理队列、最后一次错误 | 从不 |

可同步的文件就是普通 Markdown。它们位于可见的项目文件夹内，因此你已经在用的
Markdown 同步方式——默认设置的 Obsidian Sync，或者别的工具——会把它们带到各台
设备之间，不需要改动任何设置。每个文件以 `writing-buddy:` frontmatter 键开头，
标明它由插件管理，并记录引擎、schema 与制品格式的版本，后面跟着一句「请勿编辑」
的说明。文件数量随章节数增长，而不随事实数量增长；一次编辑只是往该章的包里追加
区块。区块内部带着抽取结果，因此从其他设备同步来的知识不需要任何模型调用；每个
区块都带 Recanta 的校验和，因此损坏或被手工改动的区块会被跳过，既不会被采信，也
不会覆盖本机已有的内容。这些文件绝不包含凭据、本机路径或本地数据库的位置；有测试
逐个文件检查这一点。受管文件既不算正文也不算设定，不会作为上下文被检索，插件也不
会把自己写出的内容当作新消息读回。本地索引位于 Obsidian Sync 从不上传的隐藏缓存
目录下，其中的一切都是可丢弃的：删掉这个文件夹，下次启动会从可同步的包重建，而且
不需要模型调用。仍使用早期 JSON 布局的仓库会在启动时迁移一次：每个 JSON 制品被
打包进对应的包、读回并校验，确认无误后才退役。

## 多设备同步

另一台设备收到同步文件时，无论顺序如何：

- 包内的制品在其依赖齐备时立即应用；先于所依赖的包到达的制品会等待，等依赖落地后
  再应用；同一个包重复送达、或以任意顺序送达，都不会产生变化；
- 先于正文到达的知识可以立即使用；正文落地时，引擎会识别出该版本，不会请求模型；
- 先于知识到达的正文会等待一分钟；如果知识没来，正文就在本机阅读，两份历史会在
  文件相遇时收敛，因为相同的工作会产生相同的制品；
- 损坏的包、外来的区块，或由更新版本引擎写出的区块，会被跳过并报告，绝不应用；
  它们发生变化时会被重新读取；
- 两台设备确实同时编辑了同一章时，你的同步工具保留哪份文本，记忆就跟随哪份：两份
  历史都会到达两台设备，每台设备以相同方式从共享文件重建本地索引，因此得到相同的
  知识。

## 恢复

| 情况 | 会发生什么 |
|---|---|
| 处理途中插件被关闭 | 队列在每个条目之前落盘，下次启动继续 |
| 插件关闭期间有编辑 | 启动时核对每个已跟踪文件的版本，并把差异排入队列 |
| 缓存被删除或损坏 | 下次启动时从可同步的包重建，无需模型调用 |
| 引擎升级 | 由其他引擎版本写出的索引会从包重建 |
| 包被手工改坏 | 其中的区块被跳过；「重建作品知识」会用引擎重写每一个包 |
| 部分章节失败 | 显示「部分章节未能处理」并附「重试」；其余章节照常服务；其他设备抽取的文本到达时会自动修复 |
| 连接拒绝（限流、模型冷却、服务器不可达） | 不再发出任何请求；队列等待服务器的 `Retry-After`，没有则从 30 秒翻倍至 10 分钟，然后自行继续；设置里会显示等待时间 |
| 怀疑知识已偏离 | 「重建作品知识」 |

## 移动端

`src/memory/` 下的任何文件都不引入 Node、Electron 或 Obsidian；有测试强制这一点，
另有测试在类浏览器的全局环境下、完全不使用 Node 模块打开嵌入 `main.js` 的引擎。
生命周期在两次保存之间以小步异步推进；察觉保存是同步且开销极低的，真正的工作稍后
进行。iOS 与 Android 上的真机验证——写作时的后台处理、Obsidian Sync 到达第二台
实体设备、手机上缓存丢失——仍需人工完成，见发布检查清单。
